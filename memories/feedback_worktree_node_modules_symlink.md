**ルール: git worktree 配下で frontend の `tsc` / `lint` を Ghostty 検証するとき、メイン repo の `frontend/node_modules` を `ln -s` で worktree 側に貸し、検証完了後に `rm` で symlink を撤去する。worktree 側で `pnpm install` は絶対に走らせない。**

**Why:**
- `git worktree add` で作る worktree は `frontend/node_modules` を持たず、`pnpm exec tsc --noEmit` も `pnpm lint` も `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL  Command "tsc" not found` や `Cannot find module 'zod'` 等の全滅エラーで終わる
- かといって worktree 側で `pnpm install` を走らせると、メイン repo と devcontainer が bind mount で共有している `node_modules/.pnpm` の native binding (rolldown / lightningcss 等) を darwin-arm64 で上書きしてしまい、devcontainer 側 `pnpm dev` を Build Error で停止させる ([[feedback_dev_server_ownership]] の絶対ルールに違反)
- 2026-05-13 PR #1007 レビュー対応で実際に踏み、symlink で回避 → 検証成功 → symlink rm で原状復帰の手順を確立

**How to apply:**
1. worktree で検証したくなったら、まず symlink を貼る:
   ```bash
   ln -s /Users/m-yamashita/Desktop/dev/x/kozoka-v2r/frontend/node_modules \
         /Users/m-yamashita/Desktop/dev/x/kozoka-v2r-worktree-<name>/frontend/node_modules
   ```
2. `cd` した上で `pnpm exec tsc --noEmit` / `pnpm lint` を実行 (`pnpm install` は禁止)
3. 検証完了後に必ず symlink を撤去:
   ```bash
   rm /Users/m-yamashita/Desktop/dev/x/kozoka-v2r-worktree-<name>/frontend/node_modules
   ```
4. worktree 自体も用が済んだら `git worktree remove` で消す (CLAUDE.md ルール: worktree は一時的調査用)

**注意:**
- symlink はあくまで「メインの node_modules を読み取り目的で借りる」発想。`pnpm add` / `pnpm remove` 等で書き込みが発生する操作を symlink 経由で行うとメイン側の node_modules を直接汚染するので絶対に走らせない
- 検証で `Cannot find name 'Video'` 等の本物のエラーが出た場合は素直に修正する。symlink は環境問題のみ解消し、コード問題は当然そのまま出る
- backend (Go) には不要。`go build` / `go vet` / `go test` は worktree 単独で完結する

**vitest は symlink では動かない (2026-05-21 確認):**
- `vitest@4.1.4 + rolldown@1.0.0-rc.16` の組合せで Ghostty (Mac arm64) から symlink 経由で `vitest run` を実行すると `Cannot find module '@rolldown/binding-darwin-arm64'` で startup error
- メイン repo の `node_modules` は **devcontainer (linux x64) で install されたもの** で、optional dependencies の native binding が linux 向けのみで Mac native 用は不在
- 対処: vitest 検証は **devcontainer 側でユーザに依頼** (`pnpm exec vitest run __tests__/...` を devcontainer ターミナルで実行)。tsc/eslint は native 不要なので Ghostty 側 symlink で十分動作
- spec 035 Task 1 で踏み、tsc + ユーザ vitest 依頼の運用に切替えた

**worktree 単独 install 経路 (2026-05-22 更新、ユーザ承認パターン):**
- Ghostty 側で **worktree ディレクトリ内で `pnpm install --frozen-lockfile`** を実行すると、`darwin-arm64` native binding を含む `node_modules` が worktree 配下に生成され、Ghostty から `pnpm exec vitest run` がそのまま緑化できる
- メイン repo の `node_modules` (devcontainer と bind mount 共有) は **無触** のため [[feedback_dev_server_ownership]] の「pnpm install 禁止」原則に抵触しない (禁則の本質はメイン側 binding 上書きであり、worktree は bind mount 外)
- 2026-05-22 spec 035 Phase 1 完了後の vitest 検証で実証: 113 ファイル / 1078 passed / 1 skipped / 0 failed を Ghostty 単独で PASS

**前提条件 (満たさない場合は実行禁止):**
1. devcontainer 側 `pnpm dev` を停止して bind mount 衝突懸念をゼロにする
2. 対象 worktree がメイン repo の `frontend/node_modules` を **symlink していない** ことを確認 (`ls -la <worktree>/frontend/node_modules` が directory であって symlink でないこと、もし symlink あれば先に `rm` で撤去)
3. **ユーザ承認をその session で取得済み** であること。承認なしの先行 install は禁止 — symlink 経路で済むなら symlink を優先する

**判断フローチャート:**
- tsc / eslint だけ → symlink 経路 (軽量、native binding 不要)
- vitest を回したい → ユーザに 2 択提示: (a) devcontainer 側で実行依頼、(b) worktree 単独 install 許可 (前提 1-3 を満たす場合のみ)
- pnpm dev を別ポートで起動したい → 引き続き [[feedback_dev_server_ownership]] 通り禁止

**実行手順:**
```bash
# 0. worktree に symlink が残っていれば撤去
rm /Users/m-yamashita/Desktop/dev/x/kozoka-v2r-worktree-<name>/frontend/node_modules 2>/dev/null

# 1. worktree 単独 install (frozen-lockfile で再現性確保)
cd /Users/m-yamashita/Desktop/dev/x/kozoka-v2r-worktree-<name>/frontend
pnpm install --frozen-lockfile

# 2. darwin-arm64 binding 確認 (任意)
ls node_modules/.pnpm/ | grep -i 'rolldown.*binding-darwin'

# 3. vitest 実行
pnpm exec vitest run                                    # 全件
pnpm exec vitest run __tests__/<path>/file.test.tsx     # 単発 (memory `feedback_pnpm_test_filter` 通り `--` 不要)

# 4. 用が済んだら node_modules も撤去 (容量 1GB+)
rm -rf /Users/m-yamashita/Desktop/dev/x/kozoka-v2r-worktree-<name>/frontend/node_modules
```

**派生 tip: `git add -p` で機能粒度の複数コミット化**
レビュー対応で同一ファイルに Must Fix と Should Fix が混在する場合、`printf 'y\nn\n...\n' | git add -p <file>` でヒンク単位の stage を行い、コミット粒度を機能テーマで分けると review reply の引用がしやすい (PR #1007 で 3 コミット粒度 = Must / Should2件 / Nit2件 を達成)。
